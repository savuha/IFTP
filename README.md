# ИФТП · Монитор госзакупок (без API-ключа)

Дашборд для отслеживания актуальных закупок ЕИС (zakupki.gov.ru, 44-ФЗ/223-ФЗ),
подходящих под продукцию АО «ИФТП» (Дубна): сцинтилляторы, полупроводниковые
детекторы (Si/Ge/CdTe/алмазные), спектрометры, дозиметры, радиоизотопные
приборы (толщиномеры, плотномеры, уровнемеры), блоки гамма-излучения и источники.

## Состав
| Файл | Назначение |
|---|---|
| `iftp_zakupki_dashboard.html` | Дашборд (открывается в браузере, работает без сервера) |
| `parse_zakupki_iftp.py` | **Парсер публичных страниц ЕИС** → `iftp_zakupki_data.json` |
| `update_iftp_zakupki.py` | Альтернатива: сбор через официальный API (нужен токен) |
| `iftp_zakupki_data.json` | Создаётся парсером; дашборд подхватывает его автоматически |

## Что показывает дашборд
- сумму каждой закупки (НМЦК) и суммарный потенциал по фильтрам;
- подходящие группы продукции ИФТП (с найденными ключевыми словами) и % соответствия;
- сроки: дата публикации, дедлайн подачи заявок, остаток дней (красным ≤3 дней);
- фильтры по региону, категории продукции, срочности, новизне; поиск.

## ⚠️ Почему парсинг не работал и как это исправлено
Диагностика прогонов в GitHub Actions показала: скрипт **не падал с ошибкой**, а
по всем ~34 поисковым запросам молча получал 0 результатов, зависая на каждом
запросе почти на 2 минуты (таймаут). Причина — **zakupki.gov.ru обрывает
TLS-соединение с облачных IP GitHub-хостед раннеров** (Azure US/EU), это не
связано с версткой сайта или селекторами парсера.

Исправлено:
- Workflow (`update.yml`) теперь выполняется на **self-hosted раннере**
  (`runs-on: [self-hosted, iftp-parser]`) — см. инструкцию ниже. Раннер нужно
  поднять на вашем российском VPS, чтобы запросы шли с российского IP.
- Таймаут/ретраи запроса уменьшены (25 c × 2 попытки вместо 40 c × 3) — если
  сайт всё же недоступен, job падает за минуты, а не зависает на час.
- Добавлен «предохранитель»: после 6 сетевых сбоёв подряд скрипт останавливается
  с явным сообщением, вместо того чтобы тихо перебрать все термины впустую.
- Исправлен параметр пагинации поиска (`pageNumber`, было `page`) и увеличено
  число страниц на термин (6 × 50 = до 300 извещений на термин) — чтобы
  дашборд показывал **все** подходящие закупки, а не только первые 50.
- Исправлена гонка при коммите результата (`git push` теперь с retry +
  `pull --rebase`, раньше падал при параллельном изменении репозитория).
- Ошибки HTTP/сети теперь печатаются прямо в лог job'а (не только в
  `parser.log`), чтобы сразу было видно причину, если разметка сайта снова
  изменится.

### Self-hosted runner на вашем VPS (обязательно для работы парсера)
1. В репозитории: **Settings → Actions → Runners → New self-hosted runner**,
   ОС Linux x64.
2. На VPS выполните команды, которые покажет GitHub (скачивание `actions-runner`,
   `./config.sh --url ... --token ... --labels iftp-parser`).
3. Установите как сервис, чтобы раннер работал постоянно и слушал расписание:
   ```
   sudo ./svc.sh install
   sudo ./svc.sh start
   ```
4. На VPS должен быть Python 3.10+ и pip (`sudo apt install python3 python3-pip -y`).
5. Проверьте вручную на самом VPS перед первым авто-запуском:
   ```
   python3 parse_zakupki_iftp.py --debug --limit 20
   ```
   Если снова 0 результатов — смотрите `debug/*.html`: если это HTML с капчей/
   заглушкой — проблема в самом IP/UA, если обычная страница без карточек —
   поменялась разметка, правьте `_after_label()` / регэкспы.
6. После проверки запустите workflow вручную (Actions → «Обновление закупок
   ИФТП» → Run workflow, можно с галкой `debug`) — это первый прогон с
   реального RU IP.

## Развёртывание (парсер, без регистрации)
1. Положите файлы в одну папку (внутренний портал / файловый сервер / любой статический хостинг).
2. `pip install requests beautifulsoup4 lxml`
3. Первая проверка с сохранением сырых страниц (для контроля):
   ```
   python parse_zakupki_iftp.py --debug --limit 20
   ```
   Появятся `debug/*.html` — если разметка отличается, поправьте селекторы в
   `search_notices()` / `parse_notice()`.
4. Полный прогон: `python parse_zakupki_iftp.py`
   → создастся `iftp_zakupki_data.json`, дашборд переключится на живые данные.

## Расписание 9:00 и 15:00 по Москве
Linux (cron, время сервера = московское):
```
0 9,15 * * *  cd /путь/к/папке && /usr/bin/python3 parse_zakupki_iftp.py
```
Windows (Планировщик задач): две задачи, ежедневно 09:00 и 15:00,
действие: `python.exe "C:\путь\parse_zakupki_iftp.py"`.

## Как работает парсер
1. По ~35 поисковым терминам (все категории продукции ИФТП) обходит публичный
   расширенный поиск ЕИС, отфильтрованный по дате окончания приёма заявок «не раньше сегодня».
2. Каждую найденную карточку извещения (common-info) парсит на предмет:
   предмет закупки, заказчик, НМЦК, дедлайн, дата публикации, этап.
3. Кэширует карточки в `parser_state.json` (TTL 20 ч) — повторные запуски
   скачивают только новое. Вежливые паузы 0.6–1.4 с + ретраи.
4. Скоринг по словарю ИФТП, отбрасывает ложные срабатывания (негативные слова),
   выбрасывает просроченные, метит новые (не было в прошлой выгрузке и опубликовано <36 ч).

## Настройка соответствия
Ключевые слова по категориям заданы в словаре `DICT` в парсере (и дублируются
в дашборде, кнопка «⚙ Соответствие» — хранится в браузере).
Синтаксис: `*` — любое продолжение слова (`детектор*`), `?` — один символ.
Добавляйте типовые наименования и КТРУ-коды из практики участия в торгах.

## Примечания
- Закупки с прошедшим дедлайном не показываются (фильтр при поиске + контроль на выходе).
- Разметка zakupki.gov.ru периодически меняется — при пустых полях запустите
  с `--debug` и поправьте метки в `_after_label(...)` / селекторы.
- Найденное соответствие — скрининг; перед заявкой требования КТРУ/ТЗ проверяет специалист.
- Парсинг публичных страниц законен (открытые данные), но держите паузы —
  агрессивный режим может привести к временной блокировке IP.
